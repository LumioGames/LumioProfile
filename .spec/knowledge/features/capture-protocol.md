# 采集协议与跨端关联

**本页描述完整协议方向。第一版已实现的字段、分页传输、时钟模型和转换边界见 [第一版能力](mvp-runtime.md)；原始 Protobuf、漂移拟合与持续排出尚未实现。** 普通 Trace 保留已有记录、满时丢新详细事件，循环覆盖显式选择，已由 [ADR-004](../../decisions/ADR-004-trace-overflow-policy.md) 确认。具体字段、编码、版本范围、校准参数与资源数值尚未冻结。

包与观测接口见 [SDK 契约](sdk-contract.md)，操作步骤见 [接入使用指引](../standards/integration-guide.md)，控制和分析入口见 [Agent 流程](agent-capture-analysis.md)。本协议不要求接入方修改业务消息或补齐某套游戏埋点。

## 三个独立判断

| 判断 | 回答的问题 | 不得代替 |
| --- | --- | --- |
| 关联依据 | 是否同一操作，是否有明确因果端点 | 时钟是否可比较 |
| 时间依据 | 是否同域或已校准，误差与有效范围如何 | 事件是否属于同一操作 |
| 覆盖与完整性 | 是否实际采集，端点和中间记录是否缺失 | 业务成功、失败或取消 |

身份匹配但时钟不可对齐时，仍可追踪因果，但不计算跨端耗时。时间相近但没有身份或关系证据时，只能展示邻近事件，不能声明精确关联。

## 协议与编码分层

各端保留原始时间与事件身份，写入有界缓冲后批量排出；独立工具完成校准、关联与 Perfetto 转换。批次编码优先评估标准 Protobuf，JSON 用于控制与诊断查看；最终编码须经三端开销实验确认，不能把此建议当作已发布线格式。

| 候选方式 | 特征 |
| --- | --- |
| 紧凑原始记录，工具侧转 Perfetto | 保留校准、丢弃与关联依据；采集端协议较小，作为当前设计路径 |
| 各端直接生成 Perfetto | 少一道转换，但各端承担轨道、字典、跨来源身份和丢包恢复复杂度 |
| Chrome Trace JSON | 便于兼容现有资料，高频字符串和对象成本及质量信息表达需额外处理 |

热路径不逐条构造大型 JSON 或完整 protobuf 对象。批量编码、压缩与重建放在排出或工具阶段，不能同步阻塞玩法。编码与队列本身也计入观察者成本。

## 数据类别与批次

| 类别 | 候选内容 |
| --- | --- |
| 来源描述 | sourceInstanceId、执行上下文、角色、构建、codeEpoch、标记清单、实际能力 |
| 时钟资料 | clockId、clockEpoch、数值表示、单位/频率、精度、校准样本与有效范围 |
| 事件批次 | captureId、streamId、chunkSeq、记录序号范围、时间基准、记录与局部字典 |
| 质量资料 | 实际过滤配置、覆盖窗口、丢弃原因与范围、终止原因、最后已知进度 |

事件逻辑模型如下，不是可编译的协议声明：

```text
Record
  seq                 本写入流内的记录序号
  localTime           原始本地时间或相对本批次基准的差值
  kind                begin / end / event / link / stats
  markerId            对应清单版本的标记或指标
  spanId?             同步区间身份
  parentSpanId?       已观察到的同步父区间
  operationRef?       操作或行为归组
  correlationRef?     消息或因果关联
  payload?            清单允许的有限字段
```

来源、时钟和清单引用放在批次或流描述中，避免每条记录重复字符串。每批具有独立时间基准与解码所需动态字典，不能依赖前一批的增量状态才能恢复时间和字符串。稳定标记清单作为独立必需附件；缺少清单时保留原始 ID 并报告无法解释，不能猜测名称和单位。

批次有版本、编码标识、长度与完整性检查；未知必需语义报不兼容，损坏或截断批次不能冒充完整数据。解压大小、字典和附件均受导出预算限制。跨版本扩展的跳过规则与字段编号尚待冻结。

详细记录或统计快照通过筛选后、尝试入缓冲前分配序号，因容量丢弃留下可解释缺口。Off 不产生记录序号；过滤未选中的观测不冒充丢包。Stats 更新聚合不等于逐次产生详细记录。

## 会话与事件身份

| 身份 | 含义与变化条件 |
| --- | --- |
| captureId | 协调工具创建的一次有限采集任务，不是业务房间会话 |
| sourceInstanceId | 实际来源生命周期；页面、Worker、PuerTS 环境或相应来源重建后更新 |
| streamId | 一段写入流；重新启用或 writer 重建后更新，全包内不可冲突 |
| seq | 流内递增的记录序号，不能回绕后重用旧身份 |
| clockId / clockEpoch | 时钟身份及连续区间；时钟重置或不连续后更新 |
| codeEpoch | 热更代码代次，不自动等于时钟重置 |
| 业务会话身份 | 接入方提供的房间运行代次、客户端逻辑会话等 |
| 连接代次 | 一次传输连接，重连后更新；不必改变原操作身份 |

事件引用为 `streamId + seq`，通过流描述找到来源和采集；运输批次引用为 `streamId + chunkSeq`。逻辑角色、PID、Worker 名称或房间编号都不能单独代替实例身份。

同一诊断批次重传按批次身份去重，不能生成新事件；业务重试或重复执行保留为新的观测事件，用原操作身份和实际尝试身份关联。工具不能为得到更漂亮的调用链而删除业务重复。

诊断通道重连可以补传仍保留的原批次，不更换其事件身份。业务重连更新连接身份，迟到旧输入保留原会话和原连接，不重新标成新操作。来源实例重建不得继承旧 writer 或未验证的时钟映射。

热更记录新的 codeEpoch 与清单版本。跨代区间若无法证明连续，标记不完整或跨代，不补造终点；只有实际 writer 重建才要求新 streamId。时钟连续性独立验证，不能因热更无条件重置或无条件继承。

## 原始时钟与三端接入

各端使用自己的单调计时来源，热路径不把所有事件变换成服务器时间。业务 tick 与帧序号是关联信息，不是物理时间或跨端校准依据。

| 环境 | 候选来源 | 对齐要求 |
| --- | --- | --- |
| 浏览器主线程 / Worker | performance.now，保留 timeOrigin 与精度信息 | 规范允许的关联上下文可利用原点关系，仍记录依据并用握手验证 |
| PuerTS TS / 注入原生计时 | 经验证的单调计数器及其频率 | 只有实际共用同一时钟才能声明同域；否则校准 |
| Unity Profiler 数据 | 原生捕获自带时间域 | 单独建立映射，不能仅因同属 Unity 就认定同域 |
| Node Host / Room Worker | performance.now 或 process.hrtime.bigint 等单调来源；第一版使用前者 | 记录实际来源；有证据证明同域才直接比较，否则校准 |
| 两浏览器 / 不同机器 / 真实 DS | 各自本地时钟 | 通过明确开放的诊断通道进行往返校准 |

浏览器规范支持不同上下文的时间原点映射，同时允许精度削减和抖动；不能推广成任意浏览器或任意进程的时间可直接相减。[High Resolution Time](https://www.w3.org/TR/hr-time-3/)

保留实际来源的数值表示：performance 毫秒浮点值，或其他适配器的整数纳秒、原生计数器及频率。第一版 Node 的 `node.performance.now` 直接记录毫秒，避免每条事件产生 BigInt 及转换。转换侧安全归一化，不能把超出精确范围的大整数塞进 JS number。输出纳秒单位不代表测量达到纳秒精度。[Node 毫秒时间接口](https://nodejs.org/docs/latest-v24.x/api/perf_hooks.html#performancenow) · [Node 整数时间接口](https://nodejs.org/api/process.html#processhrtimebigint) · [Stopwatch 时间接口](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.stopwatch.gettimestamp)

日期时间仅用于人类检索，不用于直接计算跨域延迟。PuerTS 不使用缩放游戏时间或每帧才更新的值作为事件时钟；计时桥接成本需要计量。外部 CPU 采样、Unity 原生附件及 GPU 来源分别描述时间域，不能套用 TS 时钟；缺少 GPU 时间映射时只报告实际可测区间时长。

## 校准样本与误差

采用四个时间点描述一次明确的诊断往返：

```text
A 发出：a1
B 收到：b2
B 返回：b3
A 收到：a4
```

在单位已统一、单次往返内频率差可忽略、传递时间非负的模型下：

```text
往返残差 = (a4 - a1) - (b3 - b2)
B 相对 A 的偏移范围 = [b3 - a4, b2 - a1]
```

端点量化误差和已知计时误差需要扩入范围。中点可作为展示估计，不是假设路径对称后的真实偏移，更不能把半 RTT 当业务单程网络耗时。此处借用四时间点方法建立观测关系，不调整系统时钟。[RFC 5905](https://www.rfc-editor.org/rfc/rfc5905.html)

每个校准样本保留原始四时间点、时钟与来源代次、请求身份、往返残差、精度和环境。重复或旧请求不能作为新样本。若模型与样本矛盾，标记无效或重新评估误差，不能通过强制归零掩盖问题。

工具侧建立有有效范围的分段映射：

```text
参考时间 = a × (本地时间 - 本地基准) + b
```

映射记录 a/b、有效本地范围、样本引用、方法版本、误差依据及是否仅为估计。只有可说明依据的范围才能标为误差界；拟合残差不能伪装成已证明的最大误差。多段映射和多跳路径传播误差，不能挑一条看起来最精确的路径而丢掉相互矛盾的证据。

校准随明确启用的采集进行，在开始、期间与结束安排有预算的异步样本；prepare 只协商，不隐式运行采集校准。样本频率、数量、漂移模型和过期阈值仍需实验确定。后台冻结、休眠恢复、长时间缺样或时钟异常后重新验证；不能激活窗口、关闭节流或暂停玩法来改善样本。

无法约束漂移时扩大不确定性或拒算跨端耗时，不无限沿用旧映射。时钟源不连续时启用新 clockEpoch，不对断点两侧强行拟合一条直线。

同域耗时优先使用本地原始差值，保留本地分辨率限制。跨域差值要携带传播后的范围；例如 5ms ± 8ms 不能作为确定的 5ms，也不能偷偷将负值改为零。关系可以已确认而时间顺序仍不确定，两者分别报告。

## 跨端关联与业务结果

operationKey 相同表示同一操作或行为归组，不自动表示因果。关系需要显式端点、身份与标记语义；relation 类型可描述 causes、confirms、corrects、observes 等，具体枚举尚未冻结。

```text
操作 O
  ├─ 预测执行实例 P → 本地预测表现
  └─ 消息 M → 权威接收 → 队列 → 执行 → 提交 C
                                  ├─ 确认/纠正 P
                                  └─ 同步更新 U → 玩家 B 的观察表现
```

此链只表示接入方提供相应证据后的能力，不要求游戏照此埋点。接入约定包括：

- 操作身份包含必要的业务会话、来源或参与者命名空间；targetTick、输入序号或实体编号不能单独充当全局身份。
- 同一操作的预测重放有不同执行实例，不能合成一次调用；权威确认或资源结算只能依据实际权威事件。
- 消息关联考虑连接代次、方向和实际重试身份；缺少区分信息时保留歧义，不伪造尝试序号。
- 快照可能聚合多个操作，不能把整个快照归因于某一个操作。另一玩家观察优先关联权威事件或状态修订，没有对应身份时不能只凭实体相同和时间接近声明观察成功。
- 拒绝、取消、重复是明确业务结果；缺少终点是记录不完整。移动、拾取和自动行为可使用行为根或权威事件根。
- 推断关系与精确关系分开，不混入标准精确关联统计；多个并行分支不能相加为端到端延迟。

插件不修改业务消息。字段按清单白名单保存，不记录键盘文本、令牌或完整世界快照；若对关联身份匿名化，必须保持本次采集中跨来源一致的映射，不能各自改名后继续声称精确关联。

## 缓冲与丢弃策略

以执行上下文为单位配置有界缓冲，并服从页面或进程总上限。事件、字典、未闭合区间、排出队列、待确认批次和质量信息全部计入预算。容量候选沿用 [插件预算](profile-plugin.md#开销与容量候选预算)，没有实测达标结论。

| 模式 | 容量不足时 | 恢复与边界 |
| --- | --- | --- |
| 普通 Trace，默认 | 保留已记录数据，拒绝新详细记录 | 排出释放容量后可继续；保留明确缺口，不静默覆盖旧数据 |
| 循环 Trace，显式选择 | 按完整批次覆盖最旧详细记录 | 声明实际保留窗口，不能保证跨批次区间起点仍在 |

有限预留区用于质量信息和已开始区间收尾，不是永不丢失保证。质量信息自身无法可靠维护时，终止该来源详细采集并报告原因；来源崩溃后无法取得终止信息则保持尾部未知。不能因此无限分配或阻塞业务。

普通 Trace 丢新期间已有 Stats 仅按原显式配置运行，不自动开启统计。也不能因为容量紧张自动切换到循环模式、调整采样粒度而不记录配置变化。

| 分类 | 含义 |
| --- | --- |
| 未开启 / 配置过滤 | 没有覆盖，不作为已选择记录的丢弃 |
| 源端缓冲满 | 已选择记录但未保存 |
| 循环覆盖 | 早期详细数据已被替换；与已排出到工具的保留数据区分 |
| 排出 / 运输失败 | 源端可能有记录，但工具端未获得 |
| 导出截断 | 数据未完整进入交付包，不能伪装成采集完整 |
| 来源退出 / 尾部未知 | 无法确认最终记录与丢弃总数 |

质量信息保存原因、序号范围或计数及其准确性。丢弃不逐条构造事件或读取时钟；精确时间不可知时用前后已知记录界定范围。质量记录走有限预留通道，不能递归制造无界的丢弃记录。

运输批次确认与重传有界，待确认数据计入容量；确认意味着达到协议约定的工具侧接收状态，持久化保证需另行声明。连接中断不无限缓存。源端、运输和导出同时涉及同一范围时记录阶段与引用，避免把同一缺失重复计数为多个业务事件。

停止、来源失联和导出分别保存最后已知进度。没有终止记录时不能据最后收到的 seq 推断尾部完全无丢失。

## 丢失后的计算边界

| 证据情况 | 允许的结论 |
| --- | --- |
| 同域、身份明确的 begin/end 均在 | 该区间墙钟耗时，仍可能含抢占和未观测工作 |
| 父区间完整，但子区间丢失 | 父区间墙钟可用；完整自身耗时未知 |
| 队列两端都在且可可靠匹配 | 这一条样本的等待；不能据此证明所有样本完整 |
| 只有一个端点 | 展示事件与缺项，不补造区间 |
| 部分操作缺失 | 保留样本的统计，注明选择偏差，不冒充总体 p99 |
| 时钟不可对齐但关联明确 | 因果链可用，跨域耗时不可计算 |

自身耗时只能相对于实际覆盖的同步子区间求并集后扣除；跨线程工作不能扣成同线程自身耗时。即使没有丢包，未观测函数也可能包含在该值内。CPU 采样、墙钟区间与 GPU 时间的测量类型分开，不能互相替代。

## Perfetto 转换

工具先校验版本和批次完整性、去除诊断重传、按来源重建流、处理时钟映射与区间关系，再生成原生 Perfetto 文件。不直接拼接不同来源文件，也不按工具收到数据的时间替换原始时间。

| 数据 | Perfetto 表达 |
| --- | --- |
| 执行上下文与逻辑分组 | TrackDescriptor；角色分组不冒充实际线程 |
| 有效同步区间 | Slice；按 spanId 配对并核验父子关系 |
| 阶段事件 | Instant event |
| 有明确因果依据的关联 | Flow；纯操作归组不自动画成因果箭头 |
| 队列深度与统计 | Counter；分布原始汇总保留，不能只存几个分位数后冒充可重新合并 |
| 丢弃、生命周期和配置 | 质量轨道及可查询元数据 |
| CPU 样本、GPU 与原生数据 | 保留实际来源和测量类型的独立表示 |

原生格式支持自定义轨道、区间、计数器和 flow。[Perfetto 转换说明](https://perfetto.dev/docs/getting-started/converting)

转换器先完成有误差依据的参考时间映射，保留原始时间、映射版本和范围。无法对齐的来源输出独立时间域或文件。ClockSnapshot 能表达映射，不负责证明网络校准精度；不能将完整漂移和误差模型隐式交给导入器处理。[Perfetto 时钟模型](https://perfetto.dev/docs/concepts/clock-sync)

区间按原始身份重建，不依赖有缺口的 begin/end 栈盲配。未闭合区间显示真实端点和不完整状态，不以采集停止时间当作业务结束。若 UI 需要可视化截断范围，必须标为观测范围并排除业务耗时统计。

轨道、Flow 和输出事件 ID 在导出包内统一分配，保留原始事件引用，不依赖无碰撞检查的简单哈希。跨端估计时间与明确因果顺序冲突时报告时间不确定，不能移动事件来制造整齐的箭头。

质量信息同时进入可查询数据，不能只存在于独立说明文字。使用 Perfetto 增量字典时遵守序列重置与丢失规则；源协议的业务观测缺失仍需自己的质量元数据，不能只依赖 Perfetto 包丢失标志表达全部情况。[TracePacket 规范](https://perfetto.dev/docs/reference/trace-packet-proto)

原始记录和校准样本作为不可变证据保留。Perfetto 文件与分析结果记录转换器、协议、Trace Processor 和查询版本，支持离线复算。

## Agent 查询与验证

标准查询先校验实际环境、覆盖和质量，再计算允许的指标。结果至少分别携带数值或范围、measurementKind、关联依据、完整性、证据引用、时钟/查询版本及源码/时间线位置；不压缩成一个无法解释的可信度分数。

同一查询在 UI 与 Agent 中使用相同口径。Perfetto 通用查询或 UI 默认自身耗时不自动证明完整语义覆盖；标准分析必须检查所选区间的质量与覆盖，必要时返回未知。

| 验证场景 | 合格标准 |
| --- | --- |
| 已知偏移、漂移与非对称往返 | 保留原样本和模型假设；真值落在声明的适用误差范围内，无法约束时拒算 |
| 后台冻结、休眠恢复、时钟断点 | 不改变环境来追求精度；旧映射不无限外推，断点明确 |
| 重连、热更、Worker/PuerTS 重建 | 旧身份不串入新会话，原始代码与时钟代次可追溯 |
| 批次乱序和重复 | 诊断重传去重，业务重试保留，流内引用稳定 |
| 丢 begin/end、丢字典、丢批次 | 后续独立批次仍可解码；不生成伪完整调用树 |
| 循环覆盖与尾部退出 | 实际保留窗口可见；无法确认的尾部保持未知 |
| 历史等待 1043ms、规则区间约 9ms | 队列和执行分开，附各自端点；不把 tick 总成本当单能力自身成本 |
| 未来约 32 tick 与 RAF/draw 节拍问题 | tick 提前量、实际等待、RAF 机会和实际绘制分别有证据；不凭 CPU 数据归因 GPU |

这些是完整验收标准，第一版已运行其中一部分，实际证据与缺口见 [验证记录](../standards/verification.md)。校准频率、误差阈值、批次尺寸、预留比例、最大未闭合区间数、重传与编码预算须在目标环境测量后确定。
